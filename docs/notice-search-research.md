# 입찰공고 검색 속도와 완전성 조사

조사: 2026-10-15 17:45~17:50 KST. 공개 운영 API의 소수 GET, 공식 나라장터 API의 제한된 조회, 운영 DB의 읽기 전용 통계 및 EXPLAIN을 사용했다. 대량 수집·요금제·저장 한도·자동 알림 조건은 변경하지 않았다.

## 결론

넓은 일자를 검색할 때마다 나라장터 전체를 읽는 방식은 즉시 조회에 적합하지 않다. 먼저 공통 검색 색인을 완성하고 최신 차수 검증을 수집 단계에서 끝낸 뒤, 화면에는 검증된 한 페이지를 DB에서 바로 반환해야 한다. 현재 DB 검색 자체는 빠르지만 최초 수집 미완료와 공고별 원천 재조회가 결과 완전성과 체감 속도를 제한한다.

맞춤 조회의 전용 화면·라우팅·클라이언트·조건 계획기·서버 선택 인자·스타일을 제거했다. 입찰공고의 공통 마감일 검색, 번호 조회, 최신 차수 검증과 자동 공고 알람은 보존한다. 과거 `#custom-search` 링크는 입찰공고로 이동한다. 아래 성능 개편 설계는 아직 적용하지 않았다.

## 현재 실측

모든 값은 소수 표본이다. API 반환 시간은 목록 API 한 번의 시간이며 화면 전체 표시 시간이나 대규모 운영 성능 보장이 아니다.

| 측정 경로 | 선택 기간·조건 | 결과 | 관측 시간 |
|---|---|---|---|
| 공통 마감일 색인 API / 공사 | 2026-07-15~2027-01-15, 검색어 없음, 첫 100건 | 부분 색인 총 534건, 다음 페이지 있음 | 714ms |
| 공통 마감일 색인 API / 용역 | 같은 기간 | 부분 색인 총 1,249건, 다음 페이지 있음 | 404ms |
| 공통 마감일 색인 API / 공사 | 2026-04-15~2027-04-15, 첫 100건 | 부분 색인 총 535건 | 300ms |
| 공통 마감일 색인 API / 용역 | 같은 기간 | 부분 색인 총 1,249건 | 289ms |
| 공통 마감일 색인 API / 공사·용역 각각 | 2025-04-15~2028-04-15 | HTTP 400, 현재 최대 367일 제한 | 98 / 111ms |

| 공식 게시일 검색 / 공사 | 2026-10-01~15, `철거`, 미마감 | 원본 39행, 취소·차수 검증 전 | 6,179ms |

색인 API는 모두 `Cache-Control: no-store`였고 CDN은 MISS였다. DB 실행 시간은 네트워크·API·브라우저 시간을 포함하지 않는다. 현재 작은 부분 색인의 2.551ms를 수십만 건 성능으로 외삽하지 않는다. 공식 게시일 검색과 마감일 색인 검색은 날짜 기준이 달라 39-11을 누락 건수로 계산할 수 없다.

## 공식 API로 직접 찾을 때의 제약

| 연산 | 공식 조회 구분 |
|---|---|
| 일반 목록 `getBidPblancListInfoCnstwk/Servc` | `1` 등록일시 / `2` 공고번호 / `3` 변경일시 |
| 검색 목록 `*PPSSrch` | `1` 공고게시일시 / `2` 개찰일시 |
| 제출마감 시작·종료일 필터 | 지원 파라미터 없음 |

직접 게시·개찰 검색은 달력 월 안의 구간으로 나눠 모든 페이지를 확인해야 한다. 12개월을 한 요청으로 전달한 실측은 공식 오류 `07`이었다. 공식 공사 검색에서 10월 1~15일, 전체 조건, `numOfRows=999`는 총 4,844건 중 999건(약 6.27MB)을 3,722ms에 반환했다. `numOfRows=1000`은 오류 없이 **10건으로 축소**되었고 응답의 페이지 크기도 10이었다. 따라서 요청이 성공했다는 사실만으로 1,000건을 모두 읽었다고 기록하면 누락된다.

공식 게시일 검색을 반복한 표본은 첫 6,179ms에서 재조회 783ms로 달라졌다. 원천과 중간 캐시, 부하의 영향을 구분할 수 없으므로 어느 한 값을 항상 가능한 속도로 제시하지 않는다. 연산에 없는 제출마감 필터를 임의로 붙이거나 게시일·개찰일로 대신 조회해서 마감일 검색의 완전성을 주장하면 안 된다.

## 실제 누락과 수집 상태

공식 번호 조회로 각각 전체 이력 1차수와 현재 미마감을 확인했으나 `철거` 색인 11건에 없었던 사례:

| 공고 | 제출 마감 | 개찰 예정 | 공식 확인 |
|---|---|---|---|
| R26BK01764096-000 | 2026-10-16 10:00 | 2026-10-16 11:00 | 등록공고, 번호 조회 157ms |
| R26BK01766493-000 | 2026-10-16 11:00 | 2026-10-16 14:00 | 등록공고, 번호 조회 137ms |

동시에 확인한 다른 원공고 중에는 최신 차수가 취소인 공고도 있었다. 그런 공고의 제외는 정상이다. 위 두 사례는 수집 미완료 상태의 실제 누락 증거이며 전체 누락 수 추정은 아니다.

운영 DB의 당시 상태:

- 색인 1,785행, `verified_at`이 있는 행 62개.
- 최초 게시 구간 완료 0개 / 대기 746개. 일부 월의 페이지 처리는 진행되므로 완료 0개가 아무 데이터도 안 읽었다는 뜻은 아니다.
- 등록·변경 커서 4개는 공사·용역 모두 **17:40 KST**까지 진행.
- 런타임의 마지막 오류 없는 확인 시각은 **17:16:50 KST**, 최근 오류는 나라장터 응답 지연.
- 현재 구현은 프로젝트가 정한 1995-10월부터 월별 게시 구간을 만든다. 이는 공식 API의 모든 연도 데이터 제공 보장이 아니다.

`fetchedAt`은 DB를 읽은 시각이다. 최초 수집 완료, 원천 동기화 완료 시각, 각 공고 검증 완료 시각을 대신할 수 없다. 현재처럼 새로운 조회 시각만 보여주면서 전수 검색이 끝났다고 말하면 안 된다.

## 느린 경로와 추가 누락 위험

1. 일반 검색은 색인에서 최대 100건씩 후보를 받은 다음, 후보마다 번호별 전체 차수를 원천 API에서 재조회한다. 한 배치에서 후보 확인은 20건, 동시 실행은 4개다. 넓은 검색은 여러 번 더 조회해야 하며 재방문 때도 검색을 새로 시작한다.
2. 검색·번호·상세 요청은 인스턴스별 IP 40회/분 제한을 공유한다. 원천 확인이 페이지마다 늘면 정상적인 넓은 검색도 429에 닿을 수 있다. 이 제한을 제거하는 것만으로 원천 호출량 문제는 해결되지 않는다.
3. 현재 서버 캐시는 인스턴스별 5분·80항목이다. 색인에 새 차수가 있어도 오래된 번호 조회 캐시가 남으면 검증을 보류할 수 있다. 최신 차수 검증은 유지하면서 수집 단계의 버전별 검증 결과를 재사용해야 한다.
4. 색인 제목으로 먼저 검색한 뒤 후보만 최신 차수로 재확인한다. 아직 수집하지 못한 제목 변경으로 새 검색어에 일치하는 공고는 후보에조차 들어오지 않는다. 등록·변경 커서와 원천 재대사가 필요하다.
5. 면허·참가 지역이 미수집된 후보는 해당 조건으로 정확하게 판정할 수 없다. 번호 응답에는 그 세부 정보가 없으므로 같은 버전에서 이미 검증한 정보의 유실을 막고, 미확인 자료를 0건으로 단정하지 않아야 한다.
6. 현재 OFFSET 페이지는 갱신 도중 앞쪽 행의 삽입·삭제로 누락·중복이 생길 수 있다. 정렬 키, 스냅샷과 변경 버전을 정해 순회해야 한다.

## 권장 개편 설계

### 수집과 검증

- 최초 전체 게시 구간 수집은 백그라운드에서 처리한다. 실제 원천 페이지 크기인 999건을 읽고 응답의 전체 건수·반환 크기를 검증한 후, 경량 검색 정보와 처리 위치를 저장한다.
- 등록과 변경을 서로 다른 커서로 10분마다 확인한다. 실패 구간은 완료로 넘기지 않는다. 시간 경계는 겹쳐 읽고 번호·차수·변경 시각으로 중복을 제거한다.
- 번호별 최신 차수·취소·개찰 상태와 필요한 참가 조건을 수집 단계에서 검증한다. `source_version`, `verified_version`, `verified_at`을 저장하고 새 변경이 들어오면 기존 검증을 무효화한다.
- 선택 날짜별 완료 범위, 원천 동기화 시각, 보류·실패 건수, 저장 한도 도달 상태를 별도로 기록한다. 완료된 시점까지의 원천 데이터에 대해 완전성을 판단한다. 원천 API 장애·지연까지 포함한 실시간 100% 무누락 보장은 하지 않는다.
- 현재처럼 진행중·마감 임박·예정만 운영 목록으로 유지한다. 게시 연도가 오래돼도 미마감이면 수집 대상이다. 과거 개찰 완료 공고의 전체 검색은 별도의 보관 범위와 용량을 정해야 한다.

### 검색 응답

- 목록 요청 시에는 원천 API를 공고 수만큼 호출하지 않는다. `검증된 최신 버전`을 DB에서 50건씩 반환한다. 미검증 후보와 확인 실패는 별도 건수·상태로 표시한다.
- 날짜·업무·상태·기관·금액·면허·지역 필터를 DB에서 적용한 뒤 페이지를 나눈다. 첫 페이지 50건만 브라우저에서 필터링하고 전체 결과라고 표시하지 않는다.
- `(마감시각, 업무, 번호)`의 고유 정렬 키와 버전 토큰으로 다음 페이지를 읽는다. 변경으로 정렬 키가 바뀌는 문제까지 막으려면 고정 스냅샷 또는 버전 보관이 필요하다. 단순히 커서만 추가해서 스냅샷 일관성을 보장했다고 하지 않는다.
- 기존 `(업무, 마감시각, 번호)` 인덱스를 활용한다. 제목 `strpos`는 현재 날짜 후보를 다시 검사하므로 규모가 커질 때 한글 부분 검색용 인덱스의 실행계획을 비교한다.
- `철거`, `석면` 같은 두 글자 검색을 반드시 별도로 실험한다. `pg_trgm`을 추가하는 것만으로 짧은 포함 검색이 빨라진다고 단정하지 않는다. 다국어 검색용 PGroonga 또는 두 글자 후보 색인과 최종 원문 포함 검사의 용량·속도를 비교한다.
- 응답 캐시 키에 선택 조건·원천 버전·페이지 커서를 포함한다. 현재 메뉴 잠금 확인을 유지하고 공용 CDN 캐시로 접근 검사를 건너뛰지 않는다.
- 현재 367일 제한은 우리 앱의 안전 제한이다. 검증된 색인 검색으로 전환하고 넓은 범위 부하를 확인한 뒤 완화한다. UI 숫자만 늘려 수년 조회를 지원한다고 하지 않는다.
- 상세·첨부파일·실제 투찰 직전 확인은 공고를 열 때 최신 원천으로 조회한다. 자동 알림의 전후 7일·10분·중복 방지 정책은 별개로 보존한다.

### 저장 용량

당시 카탈로그 전체 물리 사용량은 **4,546,560바이트(4.34MiB) / 앱 내부 상한 16MiB**였다. 색인 테이블과 인덱스는 **2,940,928바이트**, 공고 JSON 문자열 평균은 **1,187바이트**였다. 16MiB는 Supabase 요금제 전체 용량이 아니라 기존 수집기의 자체 한도다.

이 평균을 단순 적용하면 10만 건의 JSON 문자열만 약 **113MiB**다. 테이블·인덱스·버전·수집 기록은 추가로 필요하며 실제 압축률도 다르다. 수년치 전체 공고를 16MiB 안에 담는다고 약속할 수 없다. 원본을 읽고 버리는 방식은 수집 공간을 줄이지만, 버린 내용을 임의의 새 검색어로 즉시 다시 찾으려면 검색 정보 보관이나 원천 재조회가 필요하다.

진행 공고만 경량 보관하는 설계를 먼저 실제 전수 건수로 산정한다. 그래도 한도를 넘으면 보관 범위·압축 스키마·저장 한도 중 변경할 항목을 사용자에게 제시하고 승인받는다. 이번 조사에서는 한도를 늘리지 않았다.

## 검증 목표와 적용 순서

1. 최초 수집의 최근 월부터 완료시키고 실패·보류 원인을 처리한다. 누락 사례 두 건과 알려진 취소 공고를 회귀 표본으로 포함한다.
2. 검증된 공통 색인과 버전별 무효화를 만든 뒤 기존 경로와 같은 조건의 결과 집합을 비교한다. 목록 호출 중 원천 API 0회를 검증한다.
3. 1개월·1년·3년·전체 보관 범위, 공사·용역 통합, 검색어 없음·철거·석면·폐기물, 면허·지역 필터를 측정한다. 등록·변경 중 페이지 이동, 취소·개찰 완료와 날짜 경계를 검증한다.
4. 1만·10만 행의 대표 데이터에서 DB 실행계획과 첫 화면 표시 P50/P95를 기록한다. **첫 페이지 1초 이내**는 개편 목표이며 지금 달성한 성능 보장이 아니다. 캐시 적중과 미적중, 전체 건수 계산과 페이지 응답을 분리한다.
5. 결과 일치·수집 범위·용량을 확인한 후 날짜 제한 완화와 배포를 진행한다.

## 공식 근거

- [조달청 나라장터 입찰공고정보서비스](https://www.data.go.kr/data/15129394/openapi.do) 및 [공식 참고문서](https://www.data.go.kr/cmm/cmm/fileDownload.do?atchFileId=FILE_000000003665344&fileDetailSn=1): 게시·개찰 검색 및 번호 조회의 인자와 제공 범위를 구분한다. 제출 마감일은 응답 필드이며 현재 공식 검색 연산의 기간 인자로 사용하지 않는다.
- [Supabase Query Optimization](https://supabase.com/docs/guides/database/query-optimization): 조건·조인·정렬에 맞는 인덱스와 실행계획 확인.
- [PostgreSQL Multicolumn Indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html): 업무 equality와 날짜 range에 맞춘 복합 인덱스.
- [PostgreSQL LIMIT and OFFSET](https://www.postgresql.org/docs/current/queries-limit.html): 고유 정렬 필요성과 큰 OFFSET의 비용.
- [PostgreSQL pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html): 추출 가능한 trigram이 없는 패턴은 전체 인덱스 검색으로 퇴화할 수 있다.
