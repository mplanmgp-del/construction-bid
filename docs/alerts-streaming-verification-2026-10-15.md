# 공고 알람 구간 수집 운영 검증

사용자는 약 1,000건씩 읽고 일치 공고만 보관하는 방식, 처리 위치 보존, 최초 수집 후 10분마다 신규·변경 확인, 기존 MY입찰관리 자료 초기화를 승인했다. 적용 대상은 공고 알람이며 기존 맞춤 조회 화면의 검색 방식은 바꾸지 않았다.

## 실제 API와 수집 구조

- `numOfRows=1000`은 HTTP 200 / 결과 00이어도 응답이 10건으로 바뀐다. 정상 최대 크기인 999건을 사용한다.
- 1995년 10월부터 2026년 10월까지 공사·용역 각각 373개, 합계 746개 월별 게시 구간을 만든다. 현재 미마감 후보를 원천에서 거르고, 최신 전체 차수와 필요한 참가조건까지 확인해 일치 공고만 보관한다.
- 페이지의 비일치 원문·전체 본문·첨부 원문을 누적하지 않는다. 비공개 처리 건수·페이지·완료 구간과 알림 중복 방지 기록은 남긴다. 조건 변경은 별도 범위를 만들며 이전 완료 이력을 지우지 않는다.
- 등록·변경 조회를 과거 보충과 병행한다. 상세 검증이 늦어져도 내부 저장 시점의 변경 구간으로 비교해 누락을 막는다. 공급자 변경 시각은 오래된 응답 검증용으로 따로 유지한다.
- 동일 번호의 상위 차수는 내용이 같아도 변경으로 비교한다. 이전 차수 일정이 미래여도 최신 취소 차수는 진행 공고에 포함하지 않는다. 동일 회원·공고·버전의 이벤트는 고유 키로 중복을 막는다.

## 적용 및 검증

- 커밋 `55e5f8a`, 운영 배포 `dpl_B8n26WtJxY77miC2kGicEpuaC4UF`, production 별칭 READY 확인.
- 전체 86개 파일·952개 테스트, TypeScript 검사·Vite 빌드 통과.
- PGlite에서 신규 스키마 적용, 마이그레이션 2회 연속 적용, 기존 알림 및 신규 수집 SQL 회귀 검사 통과.
- 지연된 상세 검증, 같은 전체 건수에서 페이지 순서 변경, 실패 페이지 이어 읽기, 999+1 전체 차수, 조건 변경 후 재수집, 오래된 응답 거절, 상위 동일 내용 차수, 기존 알림 키 보존을 검증했다.
- 운영 익명 알림 조회 및 잘못된 작업 토큰은 각각 HTTP 401이다. 작업 토큰·구독 주소·VAPID 비밀값을 로그에 기록하지 않았다.
- 운영 상세 화면에서 제출 마감 `2027.03.04 10:00`, 개찰 `2027.03.04 11:00`을 확인했다.

## MY입찰관리 초기화

브라우저 영구 삭제의 실행 직전 확인을 별도로 받고 `supabase/maintenance/reset_company_archive_20261015.sql`을 실행했다. 대상 15개 테이블의 합계 행 수는 0이다. 업체이력·개찰 수집 cron 두 개는 비활성화했고, 설정도 모두 중지했다. 비활성 상태에서 업체 검색이 새 수집을 예약하지 않도록 보호했다.

전체 DB 크기는 약 400 MiB에서 14,874,291바이트(14.2 MiB)로 줄었다. 회원 작업공간 3개, 알림 조건 1개, 기존 알림 7개를 보존했고 관심공고 2개가 운영 화면에 유지된다. 공고 알람 cron `bid-personal-alerts`는 `*/10 * * * *` 활성 상태다.

전체 연도 확인은 그 구간에 게시된 현재 유효한 맞춤 공고를 찾는 의미다. 실제 API 지연·한도·재시도에 따라 실행 시간은 달라진다.

## 완료 결과

최초 전체 구간 수집은 16:24~16:33, 약 8분 58초에 끝났다. 746/746개 구간, 과거 구간 원천 7,046건, 일치 공고 65건·70개 차수, 상세 확인 대기 0건이었다. 최종 비교 완료 체크포인트 `__complete__`도 확인했다. 이후 신규·변경 수집은 전체 과거 구간을 다시 읽지 않는다.

기존 알림 기록에만 남아 있던 공고 4건도 전체 차수로 검증했다. 그중 이미 취소된 3건을 진행 목록에서 제외했다. 새 수집에 없던 기존 관측 공고도 추적하도록 SQL을 보완하고, 기존 중복 방지 키·버전·완료 구간을 보존했다. 신규 SQL의 재적용 및 기존·신규 회귀 검사를 다시 통과했다. 기존 공고 목록과 첫 알림의 표시 건수도 현재 유효한 공고만 계산한다.
