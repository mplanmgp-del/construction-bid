# 지역 조건 상태 조회 503 개선

## 재현과 원인

운영 주소 `https://construction-bid-nine.vercel.app/`에서 결과 요청은 200이었지만, 서울 지역을 켠 상태 조회는 약 3.3초 후 `CATALOG_STORAGE_ERROR` / 503이었다. 업종코드가 없는 기존 지역 검색에서도 재현됐다. 같은 요청을 실제 `construction-bid` 데이터베이스(`zjmhmyzgsmglrictwqtd`) RPC로 조회해 PostgreSQL `57014: canceling statement due to statement timeout`을 확인했다. 운영 anon 역할의 제한은 3초였다.

약 4,954건을 대상으로 지역 별칭 사전을 매 공고마다 펼치고, 재확인 100건을 고르기 위해 전체 후보를 다시 분류했다. 첫 별칭 캐시 최적화 후에도 직접 상태 집계 3,612ms와 확인 요청 2,904ms가 필요했다. 이후 수집 상태의 `current_coverage()`에서도 반복되는 관심 분야 제목 검사 비용을 확인했다. 운영 임시 함수로 전체 JSON 결과의 동일성을 대조한 세 차례 비교에서 731/641/643ms가 245/243/242ms로 줄었다.

## 변경

- 불변 지역 사전을 미리 만든 조회표와 정규식으로 바꾸고, 내 정보의 단일 시·도 검색을 직접 판정한다.
- 같은 정렬과 조건을 유지하면서 확인 후보를 순서대로 검사하고, 일치 100건에서 멈춘다. 기존 큐의 재시도·임대·우선순위·요청 간격과 예산은 유지한다.
- 해당 조건이 없으면 제외어 반복과 금액·날짜 파싱을 생략한다. 날짜 조건이 있으면 민간 공고도 실제 마감일을 요구하는 검사를 그대로 한다.
- 빈 배열이나 업종코드 한 개에 불필요한 집계를 생략한다. 코드 앞자리 0, 공식 코드 해석, 중복 제거와 정렬은 유지한다.
- 지역 본문을 만들 때 빈 배열에도 실행하던 집계를 직접 순회로 바꾼다. 원래 본문 필드, NFKC·공백 정규화와 지역 판정은 유지한다.
- 관심 분야의 네 가지 제목 키워드를 직접 판정한다. NFKC 정규화는 유지하며, 공백 없는 비고정 문자열 패턴의 결과에 영향을 주지 않는 공백 정리는 생략한다.

역할 시간 제한, 접근 권한, 수집 범위, 저장 한도, 사용자 설정과 알림 예약은 변경하지 않는다. 결과·건수·다음 페이지·상태 집계의 기준 시각과 버전 검사는 그대로 적용한다. 자료가 미확인인 상태를 완료로 바꾸거나 집계 대상을 제한해 오류를 숨기지 않는다.

## 검증 및 적용

2026-10-19 12:10 KST에 실제 운영 API의 아래 결과·상태 쌍 9개가 모두 200을 반환했다. 각 상태 응답의 `asOf`와 `snapshotVersion`은 해당 결과 응답과 같았다.

| 조건 | 결과 수 | 상태 HTTP | 상태 응답시간 |
| --- | ---: | ---: | ---: |
| 지역 자동 조건 끔 | 509 | 200 | 607ms |
| 서울 지역만 | 60 | 200 | 1,906ms |
| 서울 + 4995 | 1 | 200 | 2,754ms |
| 서울 + 0002 | 9 | 200 | 2,158ms |
| 서울 + 4995 또는 5652 | 1 | 200 | 2,153ms |
| 수동 서울 | 60 | 200 | 2,588ms |
| 수동 경기 | 97 | 200 | 1,966ms |
| 서울 + 4995, 미확인 지역 포함 | 1 | 200 | 2,182ms |
| 서울 + 4995, 진행중·마감 임박·예정 상태 | 1 | 200 | 2,971ms |

추가 원시 RPC 3회는 모두 200(2,225/1,927/2,352ms)이었다. 10분이 지난 조회 기준은 종전대로 409를 반환했다. 서울·4995의 공고는 `R26BK01766488`이었다. 운영 수집이 계속 진행되므로 위 건수와 지연은 검증 시점의 표본이다.

7개 SQL 마이그레이션을 같은 운영 프로젝트에 직접 적용해 각 성공 응답을 확인했다. 프런트엔드·API 소스 변경이 없는 데이터베이스 함수 개선으로, 운영 사이트가 같은 API 경로에서 새 함수를 사용한다. 적용 전후 사용자 작업공간·알림 설정 지문, 모든 예약 작업의 주기·활성 상태, anon 3초/authenticated 8초 제한이 같았다. 변경한 비공개 함수 11개에 anon/authenticated 실행 권한이 없고 `SECURITY INVOKER`가 유지된 것도 확인했다.

프런트엔드 전체 121개 테스트 파일·1,369개 검사와 타입 검사·빌드가 통과했다. SQL 검사 10개가 통과했고, 지역·프로필·업종·본문·제목 판정은 고정된 원본 함수와 별도로 대조했다. 전체 지역 판정 2만 건 이상, 프로필 판정 1만5천 건 이상, 업종 조합 24,156개, 본문 5,870개, 관심 분야 제목 2,889개에서 차이가 없었다. 격리 PGlite 5,050건 표본의 공개 RPC는 지역 924ms·수동 지역 912ms·저장 코드 1,057ms였다. 확인 대기 4,500건의 집계, 매번 100건의 확인 요청, 기존 큐 상태와 중복 처리, 시간·버전·토큰 검사, 24/32MiB 한도를 검사했다. 최종 마이그레이션 7개를 신규 설치 뒤 두 번 더 재적용해 함수 정의와 비공개 권한이 같은 것도 확인했다.

운영 Chrome에서 서울·4995의 ‘내 정보로 찾기’와 결과 1건, 펼친 자료 확인 상태의 실제 집계가 표시됐다. 최신 화면 검사 구간의 브라우저 오류·경고 로그는 0건이었다. 화면과 설정 비교는 `production-region-status.png`, `production-ui-state.txt`, `production-ui-logs.json`, `protected-settings-comparison.json`에, 최종 API/SQL 검증은 `after-acceptance.json`, `sql-regression-evidence.json`, `sql-replay-evidence.json`에 보관한다.

이 검증은 503 원인의 제거와 기존 검색 의미의 보존을 확인한다. 미확인 공고와 수집 오류는 기존 상태 정보에 그대로 남으며, 전체 수집 완료나 공고 누락 없음을 주장하지 않는다.

원시 증거와 복구 SQL은 원본 프로젝트의 `outputs/region-status-20261019/`에 보관한다. 이 폴더에는 요청에 필요한 비밀 값을 출력하지 않는다. SQL은 역할·인증·확장 기능을 모사한 격리 PGlite에서도 검사했으며, PGlite가 `statement_timeout`을 강제하지 않으므로 실제 시간 제한 통과 여부는 운영 RPC로 확인한다.
