# 정기 수집·개인 알림 운영 검증 — 2026-10-16

운영 사이트: https://construction-bid-nine.vercel.app/#alerts

실제 운영에서 10분 정기 수집, 개인 조건 비교, 웹 알림함과 푸시 발송 기록을 확인했다. 신규 공고의 실제 연결과 서비스 측 중복 방지는 확인됐으나, **검색되는 모든 공고가 10분 안에 기기에 정확히 한 번 표시된다는 뜻은 아니다.** 알림 기간 제한, 운영 중 일시 실패, 실제 변경 알림 발생 및 기기 수신 확인을 구분한다.

## 정기 실행과 검색 반영

- `bid-public-catalog`: `*/10 * * * *`, 활성. 매시 00·10·20·30·40·50분에 공사·용역의 신규·수정 원천을 확인한다.
- `bid-personal-alerts`: `1-59/10 * * * *`, 활성. 1분 뒤 개인 조건 비교와 발송을 실행한다.
- 07:52 KST 조회에서 최근 예약 SQL 실행 16건이 성공이었다. 별도로 실제 HTTP 응답을 확인했다. 07:30·07:40·07:50 수집 및 07:31·07:41·07:51 개인 비교는 HTTP 200, `ok:true`, 경고 없음이었다. 예약 SQL 성공만을 근거로 판단하지 않았다.
- 당시 공사·용역 각각 등록·수정 원천 커서 4개는 모두 07:50까지 전진했다. 수집 완료 07:50:05, 개인 비교 완료 07:51:15와 오류 없음도 확인했다.
- 예외도 있었다. 06:20 HTTP 503, 07:20 HTTP 200이지만 `ok:false`인 저장소 오류가 기록돼 있었다. 후속 주기에서는 정상 복구됐다. 따라서 10분은 시도 주기이며, 모든 변경의 검색·기기 도착을 10분 이내로 보장하는 수치는 아니다.

다음 주기를 직접 관찰한 **08:01:45 KST** 재조회에서는 다음 상태였다.

- 08:00 수집이 실제 실행됐고 원천 커서 4개가 모두 08:00까지 전진했다. 다만 원천 호출 33회 후 저장소 경고로 `ok:false`였고, 수집 전체 정상 완료 시각은 07:50에 머물렀다.
- 08:01 개인 비교는 HTTP 200, `ok:true`, 경고 없음, 2,328개 공고 자료 비교 후 08:01:28 완료였다. 비교 커서는 08:01까지 전진했다.
- 기존 신규 알림 4건은 그대로였고, 추가된 것은 직접 보낸 테스트 1건뿐이었다. 모든 발송 8건은 `sent`, 시도 1회, 대기 0건이었다. 알림함·발송의 중복 그룹은 여전히 0개였다.
- 관심 분야 확인 대기는 1건→0건으로 해소됐으나 수집 오류가 남아 `currentCoverage.complete=false`였다. 이를 수집 완료로 표시하지 않는다.
- PostgreSQL 로그에서 07:20 오류는 `P0001: Stale shared source facts`로 확인했다. 새 자료를 이전 자료로 덮어쓰지 않도록 차단한 경우다. 08:00 저장소 오류의 상세 원인은 이번 읽기 전용 점검에서 특정하지 못했다. 두 오류의 원인이 같다고 단정하지 않는다.

따라서 이 점검의 결론은 **정기 작업과 신규 알림 연결·중복 억제는 실제 동작하지만, 수집 오류가 발견돼 전체 경로 정상 판정은 보류**다.

## 실제 신규 공고의 연결

운영에 이미 생성된 신규 공고 알림 4건을 대상으로, 일반 검색 API에서 동일한 유형·번호·차수가 반환되는지 다시 확인했다. 각 공고는 알림함 행 1개, 연결된 브라우저에 대한 발송 행 1개, `sent`, 시도 1회였다.

| 공고번호 | 공고 | 검색·알림함·푸시 제공업체 수락 |
| --- | --- | --- |
| R26BK01773493-000 | 아산 풍기역지구 건설폐기물(폐콘크리트 및 혼합폐기물) 처리 용역 | 모두 확인 |
| R26BK01773420-000 | 아산 풍기역지구 건설폐기물(폐아스콘) 처리 용역 | 모두 확인 |

위 알림 생성 시각은 10월 15일 15:00~17:10 KST이며, 현재 개인 조건의 마지막 저장 시각은 같은 날 17:16이다. 이 4건을 **현재 조건을 저장한 이후 새로 도착한 공고**로 설명하지 않는다. 조건 변경 후에도 기존 알림과 중복 방지 장부를 보존한 사례다.

## 현재 개인 조건과 중복 재현

현재 계정에서 알림 받기·중요 변경 받기·푸시가 모두 켜져 있고, 해당 계정에 연결된 브라우저 구독 1개를 확인했다. 현재 조건은 검색어 철거, 공사·용역, 석면·철거/해체·폐기물 분야, 서울의 현장·참가 지역 모두 비교이며, 미확인 정보 포함이 켜져 있다. 개인정보나 푸시 구독 주소·키는 증거에 저장하지 않았다.

운영 응답의 기존 공고 4건을 실제 저장 조건으로 다시 판정했다. 4건 모두 일치했으며, 3건은 현장 정보 확인이 필요한 공고였다. 나머지 1건은 현장·참가 지역 모두 일치했다. `미확인 정보 포함` 설정에 따라 확인 필요 공고도 대상이 된 것이며, 최종 입찰 참가자격을 확정한 것은 아니다.

실제 기존 공고 1건과 현재 개인 조건을 복사해 **로컬 메모리에서만** 신규·가격 변경·차수 변경을 재현했다. 운영 공고나 알림함에 가상의 신규·변경 공고를 넣지 않았고, 이 재현에서 푸시를 보내지 않았다.

| 재현 단계 | 생성 이벤트 |
| --- | ---: |
| 새로운 공고로 입력 | 신규 1 |
| 같은 자료 재입력 | 0 |
| 같은 차수의 추정가격 변경 | 변경 1 |
| 변경 자료 재입력 | 0 |
| 내용은 같고 차수 증가 | 변경 1 |
| 같은 차수 재입력 | 0 |

운영 전체 알림함의 `(사용자, 공고, 버전)` 중복 그룹과 푸시 대기열의 `(알림, 구독)` 중복 그룹은 모두 0개였다. 현재까지 실제 `changed` 알림 행은 없었다. 따라서 실제 원천에서 새 변경이 발생해 기기까지 도달한 사례는 이번 관찰에서 확인하지 못했으며, 변경 처리에 대해서는 재현 검증과 실제 발생 관찰을 구분한다.

## 실제 테스트 푸시

07:52:53 KST 현재 계정의 연결된 Chrome에 테스트 알림을 한 번 요청했다. 운영 활성 계정과 브라우저 구독은 각각 1개였고 기존 발송 대기는 없었다. 새 테스트 알림 ID는 `38a132cf-4e62-4975-ba43-031dbb910bb8`이다.

- 운영 알림함 1건 생성, 해당 구독 발송 1건 생성, `sent`, 시도 1회를 확인했다.
- 종 팝업에도 테스트 알림 1건과 기존 신규 공고 4건이 표시됐다. 조건 저장이나 기존 알림의 읽음·삭제 상태는 바꾸지 않았다.
- `sent`는 푸시 제공업체의 전송 수락이다. 이후 사용자가 “알림이 표시됐어요”라고 답해 PC의 실제 알림 표시도 확인했다. 이번 테스트는 웹 알림함 생성 → 푸시 제공업체 수락 → PC 표시까지 확인 완료다. 운영체제 표시는 사용자 확인에 근거하며, 도구로 직접 촬영한 증거는 아니다. 다른 기기·후속 알림이나 10분 이내 도착 보장으로 확대 해석하지 않는다.
- 테스트 API의 HTTP 성공만으로 발송 완료를 판단하지 않았다. 실제 DB 발송 상태를 별도로 확인했다.

## 확인된 제한

1. **자동 알림은 마감일이 오늘 전후 7일인 공고로 제한된다.** 일반 검색의 넓은 기간과 다르다. 당시 관심 분야 투찰 가능 117건 중 마감 임박 39건, 진행중 78건이 검색 대상이었고, 그중 3건은 11월 3~4일 마감이라 자동 알림 기간 밖이었다. 이 3건은 현재 개인 지역·검색 조건에도 맞지 않으므로, 이를 현재 계정의 알림 누락 3건이라고 주장하지 않는다. 다만 사용자가 해당 공고에 맞는 조건을 저장해도 7일 제한은 별도로 적용된다.
2. **푸시 표시의 영구적인 정확히 한 번 처리는 없다.** 서버의 알림함·발송 행은 중복을 막고, 브라우저의 같은 이벤트 태그는 이미 표시된 알림을 대체한다. 제공업체 전송 수락 후 DB 처리 실패 등으로 재전송될 수 있으며, 사용자가 이미 닫은 알림까지 기억하는 영구 수신 장부는 없다.
3. 변경 알림은 설정이 켜져 있고, 변경된 공고가 알림 대상에 남는 중요한 변경일 때 생성된다. 취소·개찰 완료 등 대상에서 빠진 공고는 새 알림에서 제외하는 현재 구현이다. 모든 종류의 상태 변경을 알린다고 해석하면 안 된다.
4. 원천 재시도·검증·호출량·발송 대기·기기 정책으로 지연될 수 있다. 수집과 개인 비교도 1분 간격으로 분리돼 있다. 실제 기기 도착 10분 보장은 확인되지 않았다.

조회 범위를 모든 진행 공고로 맞추려면 알림의 7일 제한을 조정해야 한다. 기기 표시까지 추적하려면 브라우저 수신·표시 확인과 지속적인 수신 중복 방지를 추가해야 한다. 이번 요청에서는 동작을 검증했으며 개인 조건·수집 범위·알림 동작을 임의로 변경하지 않았다.
