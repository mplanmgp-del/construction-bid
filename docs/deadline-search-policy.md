# 제출마감일 검색 및 공고 알람

기준: 2026-10-15 사용자 승인 후 구현한 코드. 아래 정책은 이번 검색 개편의 구현 내용이며, 운영 DB 적용·배포·실제 수집 완료 여부는 별도 운영 검증 근거로 확인한다. 17:45~17:50 KST의 개편 전 측정값과 미완료 상태는 [입찰공고 검색 성능 조사](notice-search-research.md)에 당시 기준으로 보존했다.

## 입찰공고 검색

- 날짜 기준은 `deadline`(입찰서 제출마감)이다. 기본은 한국 날짜 오늘의 이전 6개월부터 이후 6개월까지이며 시작일과 종료일을 모두 포함한다.
- 전후 1·3·6개월, 전후 1·3년 버튼은 양쪽에 같은 달력 기간을 적용하고 즉시 조회한다. 월말은 해당 월의 마지막 날로 보정한다. 수동 날짜와 `전체 보관 범위`는 `1995-10-01`~`2100-12-31` 안에서 조회한다. 기존 367일 상한은 새 검색 경로에서 제거했다. 이 날짜 범위는 앱의 입력 경계이며, 모든 연도의 자료 보관·원천 제공·수집 완료를 뜻하지 않는다.
- 화면은 `/api/notices?mode=search` 한 번으로 공사·용역을 통합 조회한다. 선택한 제출마감 구간의 **검증된 최신 공통 색인**만 읽으며, 목록 요청 중 공고별 번호·지역·개찰 결과를 원천에서 다시 조회하지 않는다. 제공기관의 게시일·개찰일 검색으로 제출마감 검색을 대체하지 않는다.
- 공고명·검색어·제외어·업무·분야·상태·계약 방법·금액·면허·지역·업체 소재지 필터를 서버에서 적용한 뒤 전체 정렬과 50건 페이지 분할을 수행한다. 브라우저는 응답의 항목·순서를 그대로 표시하며, 첫 페이지에만 추가 필터를 적용해 전체 결과처럼 표시하지 않는다. `totalCount`는 적용 조건에 맞는 전체 색인 결과 수다.
- 상세 검색 조건 변경은 200ms 동안 모아 새 검색을 시작하고 기존 요청을 취소한다. 날짜 버튼이나 상단 검색은 현재 상세 조건을 유지한다. 업체 소재지 비교가 필요한 경우에만 시·도와 시·군·구를 전송하며 업체명·연락처·이메일은 검색 인자에 포함하지 않는다.
- 진행중·마감 임박·예정만 현재 목록에 표시한다. 제출마감이 지났어도 개찰이 미래이면 개찰 대기로 포함한다. 최신 차수의 취소, 개찰일 경과, 공식 개찰 완료, 제출마감 미확인 자료는 제외한다. 과거 차수를 최신 취소·변경 공고 대신 표시하지 않는다.
- 공고번호 직접 조회·이전 차수·상세·공개 결과는 기간 제한과 별개의 이력 확인 기능이다. 상세를 열면 필요한 최신 원천 정보를 조회한다. 관심공고 및 기존 알림함의 원본 기록은 보존한다. 별도 맞춤 조회 화면과 저장한 알림 조건을 수동 검색에 자동 적용하는 기능은 제거한 상태를 유지한다.

## 페이지 일관성과 표시

응답의 `snapshotVersion`은 색인 세대, `asOf`는 상태 판정 기준 시각, `validUntil`은 해당 판정과 커서의 유효 경계다. 다음 페이지는 같은 조건·세대·기준 시각을 가진 서명된 커서를 사용한다. 색인이 바뀌거나 기준 시각이 만료되면 서버는 `409 SEARCH_CHANGED`를 반환한다. 브라우저는 서로 다른 세대나 `asOf`의 페이지를 합치지 않는다.

브라우저는 응답을 받을 때와 캐시를 다시 표시하기 전에 `validUntil`을 확인한다. 화면을 그대로 둔 경우에도 반환된 경계 시각에 이전 결과임을 알리고 페이지 이동을 차단한다. 만료되거나 변경된 결과는 안내와 함께 남기고 사용자가 `처음부터 다시 검색`을 눌러 새 검색을 시작한다. 자동 재시작을 반복하지 않는다. 첫 페이지와 최근 페이지를 합해 최대 10개 페이지의 본문을 메모리에 보관한다.

최초 수집 범위, 검증 대기 건수, 선택조건 판정 대기 건수, 원천 변경 확인 시각, 오류, 저장 한도를 별도로 표시한다. 선택조건 판정 대기는 현재 선택한 지역·면허 조건의 판정 불확실성이며, 모든 공고의 참가조건 수집 완료 여부를 뜻하지 않는다. `fetchedAt`이나 `asOf`가 최근이라는 이유로 전수 수집·원천 동기화 완료라고 표시하지 않는다. 수집·검증이 남아 있으면 결과 0건은 원천에 해당 공고가 없다는 증거가 아니다.

## 공고 알람

- 한국 날짜 오늘 이전 7일부터 이후 7일까지의 제출마감과 회원별 알림 조건을 함께 적용한다. 진행중·마감 임박·예정 범위만 발송하며, 발송 직전 최신 차수·날짜·취소·개찰 완료 상태를 다시 검사한다.
- 공통 원천 수집과 알람 발송을 별도 작업으로 실행한다. 수집은 매시 00·10·20·30·40·50분, 알람은 01·11·21·31·41·51분으로 **각각 10분 간격**이며 발송을 수집보다 1분 뒤에 배치했다. 알람이 매분 실행된다는 뜻은 아니다. 두 HTTP 실행은 각각 43초 작업 예산 안에서 진행한다.
- 회원별 공고·변경 버전과 전달 중복 방지 기록을 보존한다. 범위 밖·완료·취소 변경은 재발송하지 않으며 중복 방지 기록은 갱신한다. 사용자가 알림을 삭제해도 중복 발송 방지 기록은 초기화하지 않는다.

## 수집과 저장

공통 색인은 회원 조건과 독립적이며 활성 개인 알림 조건이 없어도 수집·검증한다. 개인 조건 변경으로 과거 원본을 다시 수집하지 않는다. 원본 페이지는 실제 제공기관 상한인 999건씩 읽고, 최대 200건의 경량 배치로 색인을 저장한 뒤 처리 위치를 기록한다. 본문·첨부파일을 장기 보관하지 않는다.

최신 차수·취소·개찰 상태·필요한 참가조건을 백그라운드에서 확인한 공고만 검색에 공개한다. `source_version`과 `verified_version`이 맞아야 하며, 새 변경이 들어오면 이전 검증을 무효화한다. 실패·시간 초과·호출 한도 때문에 확인하지 못한 공고는 검증 대기로 남긴다. 저장 전 원천 페이지 위치를 완료로 넘기지 않는다.

공식 API는 제출마감 기간 검색을 제공하지 않으므로 최초 공통 색인 보충에는 넓은 게시 구간 확인이 필요하다. 최신 월을 먼저 읽으며 최초 수집·검증이 끝나기 전에는 `indexCoverage.complete=false`와 대기를 표시한다. 화면 검색은 이 백그라운드 수집과 별개이며, 검색할 때 다른 게시 기간을 추가로 읽지 않는다. 등록·변경은 독립된 커서로 이어서 확인한다.

공통 카탈로그 **16MiB**, 알림 관계 합산 **32MiB**의 기존 내부 상한을 그대로 유지한다. 이는 Supabase 요금제의 전체 저장 용량과 별개다. 한도에 이르면 수집을 대기하고 실제 상태를 표시한다. 한도 증가는 사용자 승인이 필요하다. 읽고 버리는 방식만으로 임의의 새 조건으로 검색할 수 있는 수년치 색인을 무제한 보관할 수 있다고 설명하지 않는다.

## 개편 전 기준과 로컬 검증의 범위

17:45~17:50 조사 당시에는 `mode=deadline`, 업무별 100건 후보 조회 후 공고별 원천 재확인, 367일 제한을 사용했다. 당시 색인 1,785행·검증 시각 보유 62행·최초 게시 구간 완료 0개/대기 746개라는 측정은 그 시점의 증거다. 이번 코드 변경만으로 그 수집 대기가 모두 해소됐다고 갱신하지 않는다.

새 검색 함수의 로컬 PGlite 합성 데이터 표본은 1만 행에서 약 275~537ms, 10만 행에서 약 2.2~3.3초였다. 이는 임시 PostgreSQL 환경의 로컬 실행 시간이며 운영 데이터 분포·Supabase 네트워크·Vercel·브라우저 렌더링을 포함한 실사용 SLA가 아니다. 운영 측정과 수집 완료 근거는 별도로 추가한다.
