# 맞춤공고 알리미 운영

2026-10-16 반복 원천 충돌을 보호된 재검증으로 복구하고, 자동 알림의 숨은 7일 제한을 제거했다. 실제 맞춤 공고를 우선 확인해 다음 10분 정각에 재검증하며 정기 개인 비교가 수동 실행 때문에 생략되지 않도록 수정했다. 기존 조건·중복 방지 장부·인증·저장 한도는 유지한다. 현재 운영 수치와 확인 범위는 [복구 및 정기 알림 검증](alerts-repair-verification-2026-10-16.md)을 참조한다.

회원은 `#alerts`에서 공사·용역 관심 조건을 저장하고 신규 공고, 주요 변경, 취소를 확인한다. 서버 작업을 연결하면 브라우저가 닫혀 있어도 수집한다. 배포 완료 여부, 실제 수집 실행, 브라우저 푸시 수신은 각각 별도로 확인해야 한다.

## 수집과 개인 조건

- 회원마다 조건 한 세트를 저장한다. 관심·제외 검색어, 업무, 분야, 지역, 면허, 추정가격, 발주·수요기관, 계약방법, 제출 마감까지 최소 남은 일수, 미확인 조건 포함 여부를 지정한다. 서로 다른 조건은 모두 적용하며 같은 입력란의 여러 값은 하나 이상 일치하면 된다.
- 공사·용역 모두 지역 기준을 `업무별 기본`, `현장 위치`, `참가 가능 지역`, `현장·참가 지역 중 하나`, `현장·참가 지역 모두` 중 선택한다. 새 조건의 기본값은 둘 중 하나다. 기존 저장 조건에 기준이 없으면 공사는 현장, 용역은 참가 가능 지역을 사용하는 기존 의미를 유지한다. 현장 위치가 제공되지 않으면 기관 주소나 참가 지역으로 추정하지 않고 확인 필요로 처리한다. OR 비교에서 한 축이 명시적으로 일치하면 충분하며 AND 비교에서는 두 축이 모두 일치해야 한다.
- 등록한 내 업체 소재지와 참가 가능 지역을 비교하거나 보유 면허와 공고 면허의 관련성을 비교할 수 있다. 면허명은 공백·가운뎃점·업종코드 표기를 정규화한다. 복수 면허의 AND/OR 조합이 원천 목록에 없으므로 일부 면허가 겹치더라도 조합 확인 필요로 표시하며 최종 참가 자격 충족을 확정하지 않는다.
- 기관은 공고에 제공된 발주·수요기관명 일부 일치, 계약방법은 방법명 일치로 비교한다. 최소 남은 일수는 현재 시각부터 **제출 마감**까지의 24시간 단위 기간이다. 참가등록 마감과 다르다. 미제공 값은 확인 필요이며 `미확인 공고 포함` 설정으로 제어한다.
- 기존 공고 카드에는 현재 저장한 조건의 일치 사유와 확인 필요 항목을 표시한다. 새 알림 메시지에도 비교 사유와 미확인 항목을 함께 남긴다. 알림을 확인하는 동안 입력한 미저장 조건은 카드 판정에 사용하지 않는다.
- `이 조건으로 알림 받기`는 현재 공고 검색어와 상세 조건을 알림 설정으로 가져온다. 알림 화면에서 저장해야 적용된다.
- 서버는 등록일과 변경일을 조회한다. 같은 원천·업무·공고번호의 최신 사실을 비교하며, 제목·금액·일정·지역·면허·취소·첨부 링크 등 주요 내용이 달라질 때 버전을 올린다. 상위 차수는 내용이 같아도 별도 변경으로 알리며, 단순 재조회와 시간 경과에 따른 마감은 새 변경 알림을 만들지 않는다.
- 같은 회원·공고·버전의 알림과 같은 알림·브라우저 구독의 전송 작업에는 고유 키가 있다. 여러 조회 구간에 겹쳐도 웹 알림을 반복 삽입하지 않는다.
- 최초 활성화나 조건 변경 뒤에는 API가 제공하는 1995년 10월부터 현재까지의 게시 구간을 월별로 확인한다. API의 정상 최대 크기인 999건씩 읽고, 개인 조건에 맞을 가능성이 있는 압축 후보만 상세 확인 대기열에 남긴다. 공고번호로 전체 차수와 필요한 참가조건을 검증한 뒤 일치한 공고만 보관한다. 기존에 보관한 공고의 변경·취소도 추적한다. 읽은 원문과 비일치 자료는 누적하지 않는다.
- 완료한 구간·처리 건수·다음 페이지는 비공개 저장소에 기록한다. 단순 시간 초과는 이어서 처리하고, 원천 전체 건수 변화나 중복 페이지가 확인된 구간만 다시 검증한다. 조건 변경은 별도 수집 범위를 만들고 이전 완료 기록을 보존한다.
- 기존 공고는 개별 신규 알림 대신 한 묶음의 건수를 갱신한다. 전체 구간 확인과 상세 검증이 끝나야 최초 수집 완료이며, 모든 연도의 마감된 원문을 저장한다는 뜻은 아니다. 화면의 구간 수와 상세 확인 대기를 함께 확인한다. 최초 수집 10~30분은 실측 일부에 기반한 예상치이며 API 한도·실패·조건 범위에 따라 더 오래 걸릴 수 있다.

## 서버 연결

### 비교 조건 확장 적용 순서

이미 알림 스키마가 설치된 운영 DB에는 `supabase/migrations/20261015030000_alert_comparison_options.sql`을 먼저 적용한 뒤 웹·서버를 배포한다. 이 마이그레이션은 기본 설정 및 검증 함수 두 개만 교체하며 기존 회원 조건·공고·수집 일정·저장 한도는 변경하지 않는다. DB가 구버전이면 새 조건이 서버 검증 과정에서 제거되므로 웹만 먼저 운영 배포하지 않는다.

2026-10-15 로컬 검증에서 전체 718개 테스트, 타입 검사 및 빌드가 통과했다. 임시 PostgreSQL(PGlite)에서 새 설치, 기존 스키마 위 마이그레이션 2회 연속 적용, 기존 및 신규 SQL 회귀 테스트가 통과했다. 예시 데이터 화면에서 5개 신규 필드 저장과 공사·용역 비교 사유 표시를 확인했고, CSS 화면 폭 1276px 및 386px에서 가로 넘침이 없음을 확인했다. 이 기록은 로컬 검증이며 운영 적용 성공을 뜻하지 않는다. 해당 시점에는 Supabase 관리 계정 권한 및 Chrome 연결 문제로 운영 DB 변경을 적용하지 못했다.

같은 날 Chrome 연결 복구 후 운영 DB에 위 마이그레이션을 적용했다. SQL 검증 결과 `new_default=either`, `legacy_basis=auto`, 새 조건 5개 보존, 두 함수의 `security_invoker=true`가 확인됐다. 앱 소스 `8bf157e`를 운영 배포 `dpl_G9iXzasyceadHCN4yScmHtMvA7kJ`로 배포하고 `construction-bid-nine.vercel.app` 별칭의 READY 상태를 확인했다. 운영 알림 API는 익명 요청에 정상 401을 반환하며, 로그인된 운영 화면에서 알림함·새 비교 입력란·기존 푸시 연결을 확인했다. 사용자 지역 비교 기준은 `현장·참가 지역 중 하나`로 저장하고 새로고침 후 유지됨을 확인했다. 이번 비교 기능 검증에서는 테스트 푸시를 새로 요청하지 않았다. 운영 SQL 및 화면 근거는 로컬 `outputs/alerts-2026-10-15/comparison-live-*`에 보관했다.

기존 회원 저장소와 메뉴 권한 SQL이 적용된 환경에 `supabase/alerts.sql`을 적용한다. `pg_cron`, `pg_net`, Vault를 사용할 수 있어야 한다. 운영 배포에 다음 알림 전용 환경변수를 설정한다.

| 이름 | 용도 |
| --- | --- |
| `ALERT_WORKER_TOKEN` | 수집 작업 인증. Base64URL 문자로 된 43~128자 서버 비밀값을 사용한다. |
| `ALERT_VAPID_PUBLIC_KEY` | 브라우저 푸시 공개 키. 서버가 필요한 화면에 공개 값만 전달한다. |
| `ALERT_VAPID_PRIVATE_KEY` | 공개 키와 짝을 이루는 푸시 서명 비밀 키. |
| `ALERT_VAPID_SUBJECT` | 푸시 운영자 연락용 `mailto:` 주소 또는 유효한 HTTPS 주소. |

기존 `G2B_SERVICE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`도 필요하다. 알림 전용 네 변수에 `VITE_` 접두사를 붙이지 않는다. 작업 토큰·VAPID 비밀 키·푸시 구독 주소를 브라우저 코드, 문서, 로그에 기록하지 않는다.

관리자로 로그인해 알림 화면의 `서버 알림 설정`을 실행한다. 설정 함수는 작업 토큰을 Vault와 비공개 해시에 저장하고, 이름이 `bid-personal-alerts`인 작업을 10분마다 실행하도록 연결한다. 이 이름의 작업만 갱신하며 기존 업체이력 수집기의 스케줄과 예산은 유지한다. 수집기 연결에는 작업 토큰이 필요하며 브라우저 푸시는 VAPID 설정을 추가해야 사용할 수 있다.

연결 뒤에는 명명된 작업 존재, 실제 작업 실행 결과, 화면의 마지막 확인 시각과 수집 범위를 순서대로 확인한다. 환경변수나 코드 배포 성공만으로 상시 수집이 확인된 것으로 보지 않는다.

## 브라우저 푸시

웹 알림함은 푸시 권한 없이 사용할 수 있다. 푸시는 회원이 `이 브라우저 알림 켜기`를 누를 때 권한을 요청하고, 현재 계정과 브라우저 구독을 연결한다. 다른 기기에서는 별도로 켜야 한다. 차단된 경우 브라우저 사이트 설정에서 허용하고 다시 설정한다. 아이폰·아이패드는 홈 화면에 추가한 웹 앱에서 이용한다.

`테스트 알림`으로 서버 발송과 해당 기기의 수신을 확인한다. 서버 발송 완료와 실제 알림 표시는 별개다. 운영체제 알림 설정, 브라우저 정책, 절전과 네트워크 상태에 따라 지연될 수 있다. 로그아웃 시 현재 브라우저의 연결을 해제하며, 다른 계정이 사용 중인 구독을 임의로 가져오지 않는다.

일시 실패는 전송 대기열에서 제한된 횟수로 재시도한다. 만료된 구독은 해제한다. 전송 성공 직후 상태 저장이 실패하는 경우처럼 푸시 제공자와 DB 사이에는 한 번만 전달되는 것을 보장할 수 없는 구간이 있다. 웹 알림의 고유 키와 브라우저 알림 태그로 중복을 줄인다.

## 한도와 오류

알림 관계와 인덱스에는 기존 32 MiB 합산 한도를 유지하고, 2026-10-16 현재 관심 공고 수집 작업에서 이 안의 공고 색인 배정을 최대 24 MiB로 조정했다. 첨부서류와 본문은 상세 열람 시 원천 API에서 가져온다. 저장 한도를 자동으로 올리지 않는다.

2026-10-15 사용자의 명시적 승인으로 `supabase/maintenance/reset_company_archive_20261015.sql`을 별도 실행했다. MY입찰관리의 업체·참여·낙찰·계약 자료 및 수집 이력 15개 테이블은 0건이며, 해당 cron 두 개와 수집 설정을 중지했다. 회원 작업공간·관심공고·알림 설정·알림함은 보존했다. DB 실측은 약 400 MiB에서 14.2 MiB로 감소했다. 공고 알람의 10분 cron은 유지한다.

새 저장 배치가 한도를 넘으면 수집을 대기하고 마지막 확인 시각과 오류를 표시한다. 기존 자료를 자동 정리하거나 한도를 자동으로 올리지 않는다. 운영자는 실제 크기와 원인을 확인한 뒤 후속 조치를 정한다.

원천 조회가 실패하거나 페이지가 불완전하면 해당 최신 조회 구간의 커서를 넘기지 않는다. 현재 구간은 먼저 저장하며, 과거 보충 조회 실패는 그 과거 날짜를 유지하고 최신 공고 확인을 계속한다. 관리자 입찰공고 메뉴 잠금은 새 수집을 멈추며, 회원의 알림 끄기는 수집·전송 조건에 반영된다. 브라우저의 60초 갱신은 알림함 상태 확인이며 서버 수집을 대신하지 않는다.

10분은 서버 확인 주기다. 원천 공개 지연, 호출 한도, 저장 한도, 작업 실패 또는 기기 정책이 있어 10분 안에 모든 푸시가 도착한다고 보장하지 않는다. 오류가 있으면 마지막 확인 시각·확인 범위·보충 상태를 함께 확인한다.
